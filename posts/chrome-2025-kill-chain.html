Overview

Stage 1: V8 Type Confusion (CVE-2025-13223)

The entry point. A JIT optimization flaw in TurboFan's redundancy elimination pass incorrectly removes CheckMaps validation nodes, allowing type confusion between different object memory layouts.

Root Cause: Side-Effect Blindness

TurboFan's optimizer assumes that certain operations have no side effects. But .toString() can trigger user-defined callbacks that change object shapes:

exploit_v8.js — type confusion trigger
function vulnerable_opt(arr, trigger_obj) { let x = arr[0]; // TurboFan assumes arr contains Doubles trigger_obj.toString(); // Side-effect changes arr to Object array arr[1] = 1.337e-308; // Type confusion: float written as pointer } // After ~10000 calls, TurboFan optimizes and removes CheckMaps // The .toString() side-effect is not tracked by the optimizer // Result: attacker writes a controlled float value as a tagged pointer

The optimizer sees arr as a Double array and generates machine code that writes 1.337e-308 as a raw 64-bit float. But after the .toString() side-effect, arr is now an Object array — the float bits are reinterpreted as a heap pointer, giving the attacker a type confusion primitive.

From Type Confusion to Arbitrary R/W

  • Corrupt array length field → out-of-bounds access
  • Read adjacent heap objects → address leak
  • Overwrite BackingStore pointer → arbitrary read/write

V8 Sandbox Bypass

V8's memory sandbox (Ubercage) limits the damage of heap corruption. The attacker bypasses it by corrupting a WasmInstanceObject's jump table, redirecting WASM execution to JIT-compiled shellcode within the sandbox.

Stage 2: ANGLE GPU Process RCE (CVE-2025-14174)

With renderer code execution, the attacker escalates to the GPU process — which has kernel-level driver interactions unavailable to the sandboxed renderer.

The ANGLE Vulnerability

ANGLE (Almost Native Graphics Layer Engine) is Chrome's graphics abstraction that translates WebGL/WebGPU calls to native APIs (Metal on macOS, Vulkan on Linux, Direct3D on Windows).

CVE-2025-14174 is an integer overflow in the Metal backend when processing 3D textures with specific packing alignment parameters. The pixelsDepthPitch calculation overflows, leading to an undersized allocation:

ANGLE Metal backend — integer overflow
// Simplified vulnerable calculation: pixelsDepthPitch = width * height * bytesPerPixel * alignment; // ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ // Integer overflow when dimensions are large // Allocates small buffer, writes large texture data // Triggered via WebGL: gl.texImage3D(gl.TEXTURE_3D, 0, gl.RGBA8, width, height, depth, // attacker-controlled dimensions 0, gl.RGBA, gl.UNSIGNED_BYTE, attackerData);

Exploitation in the GPU Process

  1. Heap Feng Shui: Spray GPU process heap with SharedMemory objects to create predictable layout
  2. Trigger: WebGL texImage3D call initiates the overflow
  3. Corruption: Attacker-controlled texture data overwrites adjacent object's vtable pointer
  4. Execution: Object destruction triggers a function pointer controlled by the attacker
Why GPU process matters: Unlike the renderer, the GPU process has direct kernel driver interactions (IOKit on macOS, DRM on Linux). Compromising it provides capabilities impossible from within the renderer sandbox.

Stage 3: Mojo IPC Sandbox Escape (CVE-2025-2783)

The final stage. With control of the renderer (Stage 1) or GPU process (Stage 2), the attacker forges Mojo IPC messages to escape the browser sandbox entirely.

The Mojo Flaw

The browser process's FileSystemAccess interface only validated that file paths didn't contain traversal sequences (../), but never verified whether the renderer actually owned the requested file:

Mojo exploit — forged IPC message
// Attacker hooks Mojo dispatch tables in renderer memory // Forges OnRequestFileAccess message: { message_type: "OnRequestFileAccess", file_path: "/Users/victim/Library/Application Support/Google/Chrome/Login Data", // ^ Chrome's saved passwords SQLite database access_mode: "read", handle: forged_handle_with_elevated_privs } // Browser process checks: // ✓ Path doesn't contain "../" // ✗ Does NOT verify renderer owns this file // ✗ Does NOT verify handle authenticity // // → Browser reads file with its own privileges // → Sends contents back to compromised renderer // → Attacker has user's saved passwords

The "Logic Era" of Browser Exploitation

This kill chain represents a paradigm shift. Chrome's security mitigations have made traditional memory corruption attacks increasingly difficult:

MitigationWhat it blocksHow attackers adapt
MiraclePtrUse-after-free on raw_ptrTarget logic bugs instead of memory bugs
V8 SandboxHeap corruption → arbitrary R/WChain with WASM jump table corruption
Site IsolationCross-origin data accessEscalate to GPU/browser process
CFI/CETControl flow hijackingAbuse valid code paths with wrong data

The result: attackers now abuse valid features in invalid contexts rather than corrupting memory. The type confusion in Stage 1 exploits a valid optimization pass. The ANGLE overflow exploits a valid texture upload path. The Mojo escape exploits a valid file access interface. Each component works "correctly" — it's the combination that's deadly.

Defensive Recommendations

  • Enable Strict-Origin-Isolation to prevent cross-origin data leaks
  • Disable WebGL/WebGPU in high-security contexts to eliminate the ANGLE attack surface
  • Monitor Mojo IPC traffic for unusual patterns from renderer processes
  • Keep Chrome updated — all three CVEs have been patched
  • Use hardware security keys — even if passwords are exfiltrated, 2FA blocks account takeover
